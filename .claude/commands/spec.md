# /spec — write or change the requirements of an area

Requirements here are Lean 4 objects checked by `lake exe check`. The framework is the Lake package `quintessence`; read its `README.md` first if you have not (in a project it is under `.lake/packages/quintessence/`). Its `example/` directory is a complete project: `example/Areas/Auth` is the pattern for an area written from scratch, `example/Areas/Reservation` for one extracted from existing code.

The person you work with decides what the system must do. You write the Lean, run the checker, and bring back what it found. Never decide a requirement on the person's behalf, and never weaken a claim to make the check pass.

## Starting a project (once)

If the directory has no `lakefile.toml` yet, set the project up first: follow `SETUP.md` of the framework (in a project that already has the package it is at `.lake/packages/quintessence/SETUP.md`).

## 0. The change

Work happens in a change, and a change is a git branch. If you are on the default branch, ask for a short name and create `change/<name>` from it; use the same branch name in every code repository the change touches. Commit as `spec(<name>): ...`. Several changes can be open at once, each on its own branch. Do not merge or close a change yourself: the pull request review is the approval. When you are placed on a branch that is not the default one, that branch is the change and its last name is `<name>`. The outline of a system is made on the default branch and committed as `spec(outline): ...`. Where the person does not use git for the project, skip the branch and the commits and say so: the work is then saved only by being in the folder, there is no page of the change, and parallel work happens in copies of the folder that are put together by hand.

## 1. Model and claims

An area is what the person calls one: a part of the system with its own purpose ("protection", "inventory"). When an area is too large for one state machine, give it parts, each its own model and `Area` record, named `<area>/<part>` (`protection/configuration`, `protection/runs`); the readback shows the parts together on the area's page. The word is always "part" (not sub-area, section, module or component), in the files, in what you say to the person and in what you write for other agents; the README's list of words holds for the rest. The checker refuses a name of another shape, and an area with parts has no model of its own under the bare name. What one part treats as given, another part decides: say so in its `assumptions`.

Cut parts by the things that have a life of their own (a group, a run, a place where data is stored), not by angles on one request. Parts are separate models, and two models of the same thing can disagree without anyone seeing it, so every way into the code has exactly one owning part: the part whose model says when it is accepted and what it does. A part that needs a way in another part owns names it in its `surface` as `.ruledIn "<what>" "<where>" "<owning part>" ["<action>", ...]`, takes its outcome as given, and says only what follows for its own things (enrolment is owned by the part that has groups; the storage part says only which repository an enrolled VM gets). When whether a way in is accepted depends on rules that live in another part, the owner still states the whole decision: its action carries the other part's verdict as an input ("the workflow asked for can be had"), a requirement of the owner refuses when the verdict is no, and its source names the part that rules it. A consequence can itself have consequences: an upload of VMs is matched against tag filters in one part, and the match enrols a VM in another. Name the part your consequence follows from, the nearest one, with a place that it cites too; that part names, in turn, the one before it, and the chain must end at the owner. Before you write or extend a part, read what the other parts of the area already list in `ledger/<area>/*.json` (`surface`). The checker compares the parts: a place in the code that two parts model is an open question in both, a `.ruledIn` that names a part which neither models that place nor passes it on from the part that does fails the check, and the area's page lists every shared way in with its owner.

Ask what the area does, then write or change:

- `Areas/<Name>/Model.lean`: the state, the actions, `init`, the step function (`none` means refused), and the invariant predicates. Import only `Spec.Data`.
- `Areas/<Name>.lean`: the `Area` record with journeys, walkthroughs, invariants, requirements, scope, assumptions and views. It imports `Spec.Check`, `Areas.<Name>.Model`, and every proof file. Register it in `Areas.lean` (one import, one entry in the list).

Use what is already written. Before asking, read the documents listed in `.spec/project.json` (`documents`) and anything the person points you to: product notes, design documents, READMEs, tickets. They are sources for journeys and requirements, not the truth: say what you took from where, and let the person confirm it. No particular documents or structure are required; when there are none, everything comes from the person.

Start from the journeys. A journey is one business case of the area ("enrolling VMs", "a protection run"), told as its usual course: what the person or the business wants, and the steps that get there when nothing goes wrong. Ask the person which business cases the area serves, and keep them apart: a story that puts VMs into a group and then protects them is two journeys. A journey is generic. It speaks of "a VM", "a customer", "a run", never of a particular one, and it carries no numbers (how many VMs, which run) except a threshold that a requirement states ("the fifth wrong password locks the account"). Enrolling is one step, "the operator puts a VM into the group", however many VMs there are. Write each as a `Journey` with `steps`, each `.step "<what happens, in general words>" [<concrete actions>]`. The concrete actions are only the evidence that the model takes the step; the readback does not show them or any value they produce. Give two when the step can repeat, and the readback draws a loop on it. When a journey does not start from nothing, say where it starts in `given`, in the same general words ("the group has VMs"), and give a run that gets there in `setup`. A journey begins with what a person does (on a screen or a console), what a client of the public API calls, or a schedule's turn. Nothing else starts a business case: a message, a job's result or a call from another system is what follows from one of those, and is told as steps of the journey that leads to it, or, when another part owns what leads to it, as what follows here from that part. A journey that begins with a way in of this part that another system uses (an appliance that reports, a result that arrives) is shown as what follows from the journeys of the parts that name that way in as ruled here and come to it on their way; when no journey comes to it, tell the step in the journey that leads to it. Every way in that a person, an API client or a schedule uses is told in some journey; the checker asks about each that is not, and about each journey that begins elsewhere. What a part does because of a way in that another part owns (the storage a VM gets when it is enrolled) is not a business case of its own: tell it as a journey whose first step is that way in, named `.ruledIn` in the surface, and only with what follows for this part's own things. The checker sees from the first step that it follows from the owning part's journey, and the readback shows it so on both pages: under the owning part's journey as what follows in other parts, and in this part apart from the journeys that begin here. Tell one business case once, and write it as the flow it is. A step that every run of the case takes is a `.step`. A step that can go several ways (a run starts on the schedule's turn, or when an operator asks; the jobs of a run to another vCenter, or to AWS) is a `.choice "<what happens, in general words>" [<the ways>]`, each way `.way "<its name, a few words>" [<its steps>]`: the flow splits there into one lane for each way and comes together again for the next step. A way with no steps says that this way has nothing to do there. Write a choice where the decision is made, and only for the step it changes: how a run starts is one choice and which jobs it has is another, not ten journeys that each tell both. When a way needs something set up that the others do not (the group has a replication target), write the way as a record, `{ name := "...", given := "<when it applies, in general words>", setup := [<the actions that make it apply>], sources := [...], steps := [...] }`; its `setup` is taken after the journey's own. A step after a choice that needs other evidence after one of the ways (another run's number) names it: `(Stage.step "..." [.finish 1]).or [.finish 2]`. The checker walks every way of every choice, in all combinations, and the readback says of a way which ways of the other choices it goes with when it does not go with all of them. A decision that shows at several steps is made once: write the choice at the first step it changes, and each later step it changes as `.asChosen "<what happens there>" [<ways with the same names>]`, which goes the way that was chosen and leaves out the ways that have nothing to do there. So do not write a journey for a combination: a combination that is truly special is a way of the step it changes, and the model shows what it depends on. A step that several ways take the same way is written once and used in each (`def localCopy : Step Action := .step "..." [...]`). What follows a step in another part hangs off that step. The checker asks about every two journeys that take the same steps. List the journeys in the order a person would walk through the area. Keep everything about one thing together (defining a policy, changing it, removing it), and put the things in the order of the overall flow, what must exist first coming first (the policy, then the group, then enrolling VMs into it). Say what each journey is about in `about := "<the thing>"`, in the person's word for it; the readback puts the journeys about one thing under that name, in the order the things first appear in the list. Number the ids in that order when you first write them, and do not renumber them later: an id is a name that history refers to. Do not write refusals into a journey. The readback draws the journey as a graph and hangs on every step each way the system can turn it down, and it takes those from the refusal requirements that speak about the step's action, so the negative decisions cannot be left out or invented. No identifiers or technical terms in `say`.

Then the walkthroughs. A `Walkthrough` is one specific run worth knowing, told moment by moment in the person's own words: a failure and what follows it, a boundary, something that arrives twice or never. Use `.step` for a moment the system goes along with, `.refusal` for one it turns down, and `.outcome` when what is true afterwards is the point: it carries that as a check on the state. Name the journey it is a case of in `journey`. Every way a journey's step is turned down must happen in at least one walkthrough: the journey says that the system can say no there, the walkthrough shows it saying no. The checker asks about each one that no walkthrough shows. Keep a walkthrough to a handful of moments. There are no separate examples: a concrete case with an expected result is a walkthrough that ends in an `.outcome` or a `.refusal`.

The requirements come out of both: every step and every moment needs a requirement that covers it, and the checker asks about every requirement that shows in no journey and no walkthrough.

Rules for the claims:

- Every `text` is one plain sentence the person can confirm or reject.
- When the person has not said what happens in some situation, do not decide it. Let the model refuse the action there and write no requirement for it: the checker then reports "refused in a situation no requirement covers" with an example run, and that open question is the record. Never write a requirement to silence a question the person has not answered.
- A claim you add on your own, such as an invariant you found worth stating, is a proposal: say so in its `sources` ("proposed by the agent, not yet confirmed") and tell the person.
- Give every requirement, invariant, journey and walkthrough its `sources`: where it comes from, as a history with the oldest origin first. One entry per origin: the person (and when), a document and where in it, a place in the code. When you change an existing claim, keep the entries it has and add the origin of the change, so a requirement extracted from code and later changed by a person shows both. The reviewer sees the list next to the claim. Do not invent an origin; leave the list empty when you do not know, and ask.
- A requirement's `when` is the full condition under which the action is accepted (or, with `refused := true`, refused). Where `when` holds, the checker demands that the step succeeds and satisfies `shall`. In a part with many requirements and many actions, also give `on`, the actions the requirement can speak about whatever the state (`on := fun a => a matches .enroll ..`): the search then asks `when` only for those, and takes the time of the requirement's own actions instead of all of them. When many requirements first ask why a step is refused, give the area `reason` (`fun s a => <a number for the reason the step is refused, 0 when it is accepted>`) and each such requirement `reason := some <its number>`: the search works the reason out once for a state and an action and asks `when` only of the requirements whose number it is. Both are short cuts and change nothing: `when` stays the whole condition, and must imply them.
- Keep the scope small enough that the search finishes within the budget. Add a `bound` only for values that grow without limit.
- Say what the model assumes, in `assumptions`: one plain sentence for every bound of the scope and what it cuts off ("the group takes 2 VMs here; the real limit is 100"), for everything that stands in for the outside world, for every part of the behaviour left out, and for what you took from a document without checking it in the code. The person reads these on the readback next to the journeys; a comment in the Lean reaches nobody. Name what is left out, one by one. Behind a way in the code makes checks, sets fields and branches into cases: each of them is either a claim of the model or named in an assumption ("the check that the guest tools are installed and recent enough is not modelled"), never swept up as "and the other checks", "the rest", "and so on". What is not named cannot be noticed as missing, and the check that matters later is usually one of those; the checker asks about an assumption that leaves things out without naming them. For each thing left out, think once about what goes wrong if it fails after the model's last look at it, and where that is a real risk, say so as a question to the person.
- Give `views` for everything a journey or walkthrough talks about, named and valued in the person's words ("seat s1" is "held by alice"), one per thing in the scope. The readback tells the walkthroughs in them, moment by moment; a moment that changes no view shows the reader nothing.
- Give `lifecycles` for the principal state machines of the area: one per kind of thing that has a life of its own (a protection group, a run, a copy of a recovery point at a site, a session), not one per instance and not one per view. Each is a name and a function that gives the state, in the person's words, of every possible instance of that kind: always the same number of them in the same order, with a word such as "none" where there is no instance yet. Keep the states few and free of particulars: no names, no counters, no lists. The readback draws one diagram per kind over all instances together.

## 2. Check

Run `lake exe check` from the repository root.

- A violated claim comes with the shortest run that shows it (on the area's readback page, `out/readback/<area>.html`). Show the run to the person and ask whether the model or the claim is wrong. Then fix that one.
- A claim "below target" is not a failure, but say so.

## 3. Prove the invariants

For each invariant without a proof, write `Areas/<Name>/Proofs/<invariant>.lean` proving exactly

```lean
theorem <invariant>_holds : ∀ s, Reachable init apply s → <invariant> s = true
```

and attach it with `proof := some ⟨...⟩`. Use `Reachable.induct`. When the invariant is not preserved by a step on its own, prove a stronger predicate and weaken it at the end. Put each proof file in its own namespace, as `Areas/Auth/Proofs` does.

`sorry`, `native_decide`, new axioms, `implemented_by`, `extern`, `unsafe` and `debug.skipKernelTC` are rejected by the build. If you cannot prove an invariant, leave the proof out and report it. If you find it is false, bring the counterexample to the person.

There is no Mathlib: no `tauto`, `linarith`, `by_contra` and the like; use `simp`, `omega`, `cases`, `by_cases`, `Classical.byContradiction`. The data library (`Spec/Data.lean` in the framework) has the lemmas about maps you will need most, `FMap.get?_set`, `FMap.get_set`, `FMap.get?_of_mem_keys`, `FMap.get_of_get?`, and the proofs under `example/Areas/*/Proofs/` in the framework show the usual shape.

Proof writing and proof repair after a model change are mechanical: delegate them to a cheaper model when you can. The kernel checks the result.

## 4. Open questions

The checker lists what the requirements do not say. Go through the list with the person, one question at a time, showing the situation from the readback page. Each answer becomes a requirement, a refusal requirement, a walkthrough, or an entry in `atomic` (the decision on whether an action can interleave with others inside the implementation, with the reason). Re-run the check after each answer. Leave a question open if the person has not answered it.

## 5. Existing code

When the area describes code that already exists, the model is extracted from the code. Extraction goes in three passes, with a stop for the person after each of the first two. Do not write a model before the outline is confirmed: a model of the wrong extent, or of an area cut the wrong way, costs more to undo than the stop costs.

**The outline (once for the system, on the default branch, before any area is modelled).** Its job is that every way into the code belongs to one area and one part, and that everybody sees it.
- Count the ways in from the code, not from what you happen to read. For every repository of the system, see what a way in looks like there (the annotation of an endpoint, of a message listener, of a scheduled job; a route table) and write those marks into `.spec/project.json`: `"ways_in": {"orders-service": {"files": [".kt"], "under": ["src/main"], "marks": ["@PostMapping", "@KafkaListener", "@Scheduled"]}}`. Marks are plain text; `under` and `skip` are pieces of the path. Tell the person the marks and the counts they give, once. On every run the checker then counts the lines that carry a mark and names those that no part lists (`ways in: ...: 212 in the code, 40 in no part`, the list in `ledger/ways-in.json` and on the first page of the readback). An area is not extracted while a way in of its code is in no part.
- Give every way in to an area, and inside a large area to a part, by the thing it acts on. Write each area or part as an outline: `Spec.outline "<area>/<part>" [.unread "<what it is for, in plain words>" "<where in the code>", ...] ["<what is open about its extent>", ...] (readAt := [...])` in `Areas/`, listed in `Areas.all`. `.unread` says: found, not read yet. You need the signature and the name of each way in for this, not its body. A way in you cannot give to an area is not dropped and not guessed: put it into an outline of its own (`unassigned`) and ask.
- When the person named the areas, use their names and their extent. A name that the sources do not know is a question before anything else: say what you found that could be meant, and ask.
- Name the journeys of each part, one line each, with who starts them, in the outline itself: `(journeys := [("Creating a group", "a person"), ("A run on the policy's schedule", "a schedule")])`. No steps yet. The page shows them as named, not told.
- Note what the code branches into behind a way in: one endpoint or handler often stands for several courses, chosen by a kind (a workflow, a provider, a target; a class per kind, an enumeration the code switches on). These variants are not ways in. Say them on the way in they sit behind, in the person's words, with the place where the code picks one: `.branches ["to AWS", "to another vCenter by disk copy", "from a FlashArray"] "service/WorkflowSelector.kt:40-90" (.unread ...)`. Look for them on purpose in every repository (the enumerations and the families of classes named after a kind); they are the flavours a person knows the product by. Have them counted as the ways in are: write what such a place looks like into `.spec/project.json`, `"variants": {"orders-service": {"files": [".kt"], "under": ["src/main"], "marks": [": PaymentJob(", "enum class Provider"]}}` (the same fields as `"ways_in"`: a class per kind is marked by what it extends, an enumeration by its declaration). The checker counts the marked lines and names those whose file no way in gives among the places where the code picks a variant (`variants: ...: 31 in the code, 12 named on no way in`, the list in `ledger/variants.json` and on the first page of the readback). So `.branches` names every such file: the place that picks, and the classes it picks among. Write places with the path far enough to be of one repository only (a bare `Provider.kt` names every file of that name in every repository), and several line ranges of one file as `File.kt:10-20,30-40` (commas, no spaces; anything else after the first range is dropped). Where the code makes several choices behind one way in (the kind of copy, and the platform it runs on), say `.branches` once for each choice; they add up. The count is printed by the full run only, so run it before you say the variants are named. An area is not extracted while a variant of its code is named on no way in.
- How far you read behind a way in is the person's to decide, never yours. Where you stop before the end of what a way in sets off (the job it starts, the classes that do the work), say so at the stop as a question, with what is behind and what the journeys will not show without it ("the run's job classes, one per platform, are not read: the journeys would show one generic run"). It is not a proposal the person can accept along with others, and an assumption is not the place to say it first.
- **Stop.** Show the person the outline: the areas and parts with their ways in counted, the variants behind them by name, the journeys by name, what you could not assign, and what is unclear about the extent. Ask what is wrong. Commit the outline when they agree; it is what parallel work starts from, since every part can then name every other.
When the person asks for one area only and there is no outline, outline that area and say which ways in of the same repositories you left to other areas.

**One part at a time (in parallel on their own branches, when the person wants).** For the part you take: read its ways in, propose its journeys with their steps, and **stop** for the person to confirm the journeys before the requirements are written. Then model it as the steps below say. At the stop, before there is a model, mark what you have read as `.read "<what>" "<where>"` (read, not modelled yet), so that the count says what is true, and put the proposed journeys into the outline's `journeys`. When the part is modelled, each way in you have read is modelled, read-only, ruled in another part, or left out with a reason. A part can name a way in as ruled in a part that is still an outline, as long as that outline lists the place; its journey is then shown as following from that part. Every variant named on a way in (`.branches`) is told as a way of the step it changes, under the same name, in the journey of the business case: "A protection run copies the VM" goes one of three ways, not three journeys and not one generic step. A variant is a course of its own, not a sentence: its way has the steps that course takes, in order, each an action of the model ("the disks are copied to the repository", "a job uploads them to block storage in the cloud", "an image is made of them", "a failed import is cancelled and cleaned up"), and the course has its own requirements and walkthroughs: what must hold on it, what it refuses, what it leaves behind when a step fails, what is retried and how often. So read the code of each variant to the end of what it does, and model it: the state it keeps, the outcomes of each step. One long sentence that lists what happens, on an action all variants share, is not a variant told; the checker asks about every variant told in one step, and whether one step is all there is to it is the person's answer, not yours. The checker asks for each variant no journey shows; leaving one out is the person's decision. A variant counts as shown when a way of that name has a step with an action of the way in: where the step that differs belongs to another way in, the way still begins with the action of its own. This only proves the way is there; that its sentences say what the variant does differently is yours to make true. Leaving out is the person's decision, not yours: `.leftOut` on a way in you have not read is not allowed, and one you have read stays a question until the person says yes; then wrap it, `.agreed "<who, date>" (.leftOut ...)`, and the question goes. The part is extracted when nothing of it is unread; the check line says how many are (`3 of 41 ways in not read`).

A business case in which the person only looks at things is a journey too ("looking at what is protected and when it last ran"): tell its steps with `.look "<what the person opens and sees>" "<the place of the read-only way in>"`. Such a step has no action; its evidence is the read-only entry the part lists at that place, and its screen is that entry's. Tell these for what a person really comes to look at, not for every read.

**What to ask when.** The extent, the cut into parts and the journeys are asked at the two stops, before modelling. What the code does that looks unintended ("the code accepts a refresh for a deleted cluster: intended?") never stops the work: write it into `questions`, model what the code does, and go through these with the person at the readback. Whether an action can interleave is read from existing code, not asked: say in `atomic` what you read ("one database transaction with optimistic locking on the group, GroupService.kt:210-260; read from the code") and tell the person in one sentence per part what you found; ask only where the code does not tell.

Then, for the part:

0. Orient yourself before reading code. Read what is written about the system: the documents listed in `.spec/project.json` (`documents`), and what lies around the code itself, such as READMEs, design notes, comments and tests. Follow them to the repositories they point to (`repos`, with the local checkouts in `.spec/local.json`). None of this is required to exist or to have a particular shape; use what there is. Use it to decide what one area is (one component with its own state and operations, not a whole system), where its entry points are, which repository and paths its code lives in, and what the behaviour was meant to be. Tell the person which area you will extract and from where.
   Read fresh sources. A checkout on somebody's disk is often weeks behind its repository, and a model read from it describes a system that is no longer there. Before you read a repository, code or documents, run `lake exe check` once: it fetches every checkout named in `.spec/local.json` that was not fetched within the project's threshold (`fresh_within_days` in `.spec/project.json`, one day when not given), and names each checkout that is behind its remote. Bring such a checkout up to date before you read from it: fast-forward it (`git pull --ff-only`) when it is clean and on its default branch; when it has local changes, is on another branch, or the person has said not to touch it, leave it as it is, clone a fresh copy beside it, point `.spec/local.json` at the copy, and tell the person. A repository listed in `.spec/project.json` (`repos`) with no checkout: clone it. The person can change the threshold for one task: `lake exe check --fresh-within 0` fetches now, a large number uses what is there; when they say to use what is there, do, and say in the area's `assumptions` how far behind it was.
   The documents give orientation and intent; the code is the reference for the model. Documents age: when one says which revision of the code it was written against, compare that with the checkout, and read what changed in between before trusting its details. Do not settle a disagreement yourself. When a document says something the code does not do, or the code does something no document mentions and it looks unintended, add it to the area's `questions` as one plain sentence naming both sources ("docs/holds.md says a hold lasts 15 minutes; the code releases it after 2"). It stays on the readback page until the person answers; then remove it and change the model, the code, or neither.
   The extent of the area is the person's. When they have named it ("protection"), model all of it; do not narrow it to the part that is easiest to model. If you must leave something for later, it goes into the list below, where the person sees it.
1. List the surface before you model. Go through the code and write down every way into this area: every endpoint, every message or event handler, every scheduled job that serves it. Put each in the area's `surface`. When actions of the model stand for it, say who uses it, from the code (how the endpoint is exposed, the scheduler's annotation, the listener's topic): `.person "<what it is for, in plain words>" "<where in the code>" ["<action>", ...]` for a person on a screen or a console, `.client ...` for a client of the public API, `.schedule ...` for a schedule, `.system ...` for another system (a message, a job's result, a call between services whose sender no part models); `.modelled ...` says it is modelled and leaves who uses it open, which the checker asks about. Otherwise `.readOnly "<what>" "<where>"` when it only reads, `.leftOut "<what>" "<where>" "<why>"` when it belongs to this area and the model does not cover it. In "where", name the way in itself first: the code that decides whether the request is accepted and what it does. What only passes the request on (a gateway's route in front of the service, a proxy, a client library) is not the way in; cite it after the deciding place in the same entry, and it counts as listed. So for screen, gateway, service: the service's endpoint first, the gateway's route behind it. Give it with its lines: the point where the request, the message or the timer enters the deciding code (`rest/GroupController.kt:57`), then what lies behind it if that helps. That place is how the checker knows that two parts speak about the same way in. Make the list from the code, not from the documents and not from what you chose to model. It is how the person sees which share of the area's code the model speaks about: the readback shows it with the counts, and every left-out entry is an open question until the person accepts it.
   Where the code of the user interface can be read, tie every way in a person uses to it. The user interface is one more source, not a requirement: a project without one skips this. Read which screen and which control send the request (the route, the component, the button or form, down to the call), and wrap the entry: `.onScreen "<the screen, in its own words>" "<the control>" "<where in the user interface's code>" "<picture, if any>" (.person ...)`. A way in that several screens or controls reach is wrapped once for each. The picture is of the screen as it is when the person works that control: the right tab, step or dialog, with the control on it, and not the page's first view. The journey then shows, at each step a person takes, every screen and control that reach it, each with its picture when there is one. Do it from the user interface towards the code too: a call the screens make that no part's surface lists is a way in that was missed. A way in a person can reach that no screen calls is not a step of a journey a user walks: say what reaches it instead (a client of the public API: `.client`; a person by hand: name the tool as the screen), or ask the person whether it is still used. A screen that still calls something the code always refuses is a finding: tell it. Once one part names a screen, the checker asks about every way in a person uses that names none.
   Where there is no user interface to read yet (a new project, or a new requirement whose screen is not built), designs fill the same role. Ask the person for them once: wireframes, mock-ups, a design file, a sketch, whatever exists. Tie each way in a person will use to the screen and the control of the design in the same way (`.onScreen "<screen>" "<control>" "<where in the design: the file, the frame, the link>" "<picture>" (.person ...)`), with the design's picture of the screen as the picture, kept as a file of the project. When there is no design either, say so and go on: offer to draw plain wireframes from the journeys (one screen per step a person takes, with the fields the model says the request carries and the control that sends it), show them to the person, and use the ones the person accepts. A design is a source like any other: where it shows a control the model has no way in for, or the model has a way in for a person that no design shows, ask. When the user interface is built later, its code takes the design's place in the entry.
   A picture is a file of the project (under `shots/` in its folder); one made elsewhere is copied in. Pictures can be made once for the whole system, by whoever sets the screens up, and attached part by part: attach one only after looking at it, when it shows that screen with that control and the kind of thing the step is about, and name the controls for which none fits.
   Pictures of the screens are worth having: the person recognises a business case by what is on the screen. The content matters, not the styling. There are three ways to get them; look at what the project has and offer the person the ones that are possible, cheapest first, and let the person choose, since two of them run the project's code: (1) the project has a component catalogue or visual tests (Storybook, screenshot tests): render those headless and take the pictures, no backend needed; (2) mount each screen's component, or run the user interface, in a headless browser with the data it asks for answered by fixtures in the shape of the model's states, and take a picture per screen: this installs and runs the project's code and needs the person's yes; (3) run nothing: read the labels, fields and buttons out of the templates and draw a plain wireframe of each screen, which has the content and not the look. Keep the pictures as files of the project and name each in the entries of its screen; the checker says when a named picture is missing.
   Look behind each way in for variants. One endpoint or handler often stands for several different courses, chosen by a kind the code branches on: a workflow type, a provider, a target, a strategy class per case. Each variant that changes what happens gets its own surface entry ("a protection run of a VM replicated to AWS", with the place in the code that implements that variant) and is told as a way of the step it changes in the journey of the business case (see the journeys above), or is listed as left out. An area modelled as one generic course when the code has five is not extracted.
   The measure is the area, not the repository. One repository or service often hosts several areas; code that serves another area (its endpoints, its handlers), test-only endpoints and technical start-up code are not this area's surface and are not listed, not even as left out. When you cannot tell whether something belongs to this area, do not list it and do not drop it: name it in one question to the person ("the code also does X and Y; are they part of this area?"). When the model has an action for something another area decides, because this area depends on it, say so with `.outside "<what>" ["<action>"]`.
   Say what you read. Put into the area's `readAt` the commit each repository stood at when you read it, for every repository the sources cite, code and documents alike: `readAt := [("orders-service", "4f49550"), ("docs", "9c1e2aa")]`, by the names `.spec/local.json` maps to checkouts (`"."` for this repository; `git -C <checkout> rev-parse HEAD`). The checker compares it with the checkout on every run. When a file the model cites has changed since, it asks; the question goes away only when you have read the changed files again, corrected the model where it no longer holds, and moved the commit. Do not move the commit without reading. The user interface's code and the designs are sources like the others: name their repository in `readAt` too, and when a file a screen is tied to has changed, look whether the control is still there and take its picture again. A project whose sources must not be asked for (snapshots, no network, a person who forbids it) says `"fetch": false` in `.spec/project.json`; the checker then compares with what is there and fetches nothing. Otherwise leave the freshness check on: `--fresh-within` with a large number is for a single run that must not mix a change of the code into other work (a re-cut of parts), never the habit, and say so to the person when you use it. A part that cites files and names no commit gets a question of its own.
2. Read the code. Write the model so that it does what the code does, including what looks like a quirk. Do not tidy the behaviour up; a quirk is a question for the person, not something to fix in the model.
3. Write the requirements as plain statements of what the code does, so the person can confirm or reject each one.
4. Bind the area to the code with `code := some { ... }`. Pick the adapter for the code's language (`adapters/python.py`, `adapters/kotlin.py`) and read its header: it says exactly what `setup`, `actions` and `observe` mean in that language. In general:
   - `repo` and `paths` say where the code lives in git (`repo` is `"."` for this repository, otherwise a name that `.spec/local.json` maps to a checkout under `repo_paths`);
   - `setup` builds a fresh system in a variable named `system`; put the clock and other surroundings under the test's control there;
   - `actions` gives, for every action name, the code to run (`{0}`, `{1}` are the action's arguments). The action counts as refused when that code raises. Call `refuse()` to turn a return value into a refusal;
   - `observe` lists what is compared after every step: a name, the value the model expects as text (`true`, `3`, `none`, plain text), and the expression that reads it from the code. Observe everything a caller can see.
   The mapping must stay a table of short calls. If it needs logic to make the code fit the model, the model is wrong.
5. Run `lake exe check` until the code agrees. Each difference comes with the run that shows it. During extraction the code is the reference, so fix the model.
6. "The code has operation X that the model does not use" means the model is missing something. Add it, or leave the question for the person.
